# Meet — E2EE Modernization Refactor

Context for the ECDH-bootstrap + per-sender key-chain refactor described in
[`docs/refactors/e2ee-modernization.md`](./docs/refactors/e2ee-modernization.md).
The current implementation is the v1 passphrase model in
`frontend/src/utils/media/e2ee.ts`; this refactor replaces it with v2.

## Language

**Threat model**:
The set of assumptions we make about attackers when reasoning about the
cryptographic design. Labeled A / B / C in the refactor scoping.
_Avoid_: "security model", "attacker model" (overloaded with formal-methods
meanings).

**Threat model A**:
Passive server operator + passive network observer. The SFU is honest-but-
curious; it forwards bytes but tries to read plaintext. Network attackers
can capture and replay packets. The current v1 implementation is implicitly
A.

**Threat model B (chosen)**:
Threat model A, plus an *active malicious participant* — someone who has
legitimately joined the meeting (holds the key / completed the handshake)
and acts adversarially within the protocol. They can send arbitrary bytes
claiming any sender identity. Excludes a compromised SFU.

**Threat model C**:
Threat model B, plus a compromised or malicious SFU that serves different
bytes to different recipients. Unbuildable with a single SFU.

**Server-blind**:
The SFU forwards opaque encrypted bytes (frame header + ciphertext) without
interpreting key material. It only stores and compares key *proofs*, not
keys themselves. _Avoid_: "end-to-end" by itself (ambiguous with E2EE).

**Meeting secret**:
A 32-byte secret generated by the host at E2EE-enable time. All per-sender
chains derive from it. The host distributes it to each joiner via a
per-joiner ECDH envelope: `envelope_J = AEAD(ECDH(host_priv, joiner_pub_J),
meeting_secret)`. The host is the *initial* distributor, but any current
participant who already holds the meeting secret can also admit a joiner
by signing an envelope with their own device signing key. The SFU relays
the envelope opaquely; it never sees the secret. Automatic member-change
rekey is deferred in v1; a departed participant who retained the meeting
secret can decrypt future captured media until the meeting is recreated or
a future epoch-transition protocol rotates it.

When the epoch protocol is active, the meeting secret is exported from the MLS
group state for the active epoch using a Meet-specific exporter label. It is not
carried as a separate plaintext or encrypted field in Meet epoch metadata.

**Envelope**:
A per-joiner ECDH-encrypted copy of the meeting secret, sent from host to
joiner. The joiner decrypts with their own X25519 private key to recover
the meeting secret.

**Per-sender chain**:
A key chain tied to one sender's identity, derived from the meeting secret.
Each sender has one chain; the chain is shared across all joiners (all
joiners have the same meeting secret, so they derive the same chain).
Receivers track chain tips per `sender_id`. The chain is what authenticates
a frame's sender — a frame that decrypts under `chain_X[i]` provably came
from sender X's chain. Per-joiner ECDH is the *delivery channel* for the
meeting secret, not the chain key.

**Active participant**:
A meeting participant who may deviate from the protocol. Under threat
model B, every participant is treated as potentially active.

**Honest-but-curious**:
A server that follows the protocol but tries to learn from what it sees.
The v1 / v2 SFU is assumed to be honest-but-curious.

**Sender ID**:
A 4-byte value in the frame header identifying the sender. SFU-assigned
at peer join. The SFU tracks (sender_id → peer socket) mapping opaquely;
it does not know the identity behind the sender_id, only the socket.

**Epoch protocol**:
The MLS-style group-state protocol that rotates the meeting secret across
membership changes. It feeds the existing per-sender frame-key derivation;
it does not replace frame encryption. Meet's epoch protocol is inspired by
MLS / TreeKEM, but is not intended to interoperate with RFC 9420 MLS.

**Designated committer**:
A current epoch member chosen by the SFU to author the next epoch commit.
The SFU prefers the host when available, but may choose another online
current member to avoid host-online bottlenecks. Clients accept the commit
only if it is signed by a valid current epoch member and matches the SFU's
membership delta.

**Commit attempt**:
One SFU request for a designated committer to author the next epoch commit.
If the designated committer times out or disconnects, the SFU starts a new
commit attempt with another current epoch member. Clients accept only the
first valid commit for the expected epoch and membership delta.

**Epoch transition**:
One accepted change from epoch N to epoch N+1. A room has at most one epoch
transition in flight. The SFU may batch nearby membership changes before
designating a committer; after designation, new changes queue for the next
epoch.

**Epoch acknowledgement**:
A client signal that it installed an epoch commit or welcome. Acknowledgements
do not gate epoch activation; they are used for observability, retries, and
detecting peers that are stuck and must rejoin.

**Epoch resync**:
A recovery flow used when a client misses an epoch commit or welcome. The SFU
retries unacknowledged epoch material for a short window, and clients that see
media from an unknown epoch request the latest epoch material. If resync cannot
recover the missing state, the client rejoins as a new epoch member.

**Epoch material retention**:
The short SFU-side retention window for opaque epoch commits, welcomes, and
acknowledgement state. The SFU keeps only enough recent epoch material to retry
or resync transiently disconnected peers; it does not persist epoch secrets or
long-term group history.

**Epoch overlap**:
A short receiver-side grace window during which clients can decrypt frames from
both the previous epoch and the newly installed epoch. Senders switch to the new
epoch immediately after installing it; receivers retain previous-epoch frame
keys only long enough to cover network jitter, then wipe them.

**Epoch number**:
A 32-bit unsigned counter carried in each encrypted media frame header. It
starts at 1 and increments by one for every accepted epoch transition. The epoch
number selects the meeting secret used for frame-key derivation and is included
in the frame's authenticated data.

**Epoch member**:
One live SFU peer/socket participating in an epoch, bound to a per-device
identity and an SFU-assigned sender ID. A human user may have multiple epoch
members when joined from multiple devices or tabs. Reconnects that receive a
new sender ID become new epoch members.

**Epoch roster**:
The client-verified membership map for an epoch. It binds SFU-assigned sender
IDs to epoch members, device identities, and frame signing public keys. Clients
derive it by applying the SFU-published membership delta to the previous roster,
verifying new epoch key packages, and checking that the designated committer's
epoch commit signs the resulting roster hash.

**Epoch key package**:
The join credential published by a prospective epoch member. It contains the
member's epoch public keys, SFU-assigned sender ID, user ID, and device ID,
and is signed by the member's existing per-device Ed25519 identity key. The SFU
may relay and bind the package to room membership, but clients verify the
signature before accepting it into an epoch transition. Meet key packages are
MLS-style but live-only: they include an epoch signing public key, an
HPKE/X25519 init public key, and a leaf public key, but do not include offline
one-time prekeys.

**Key-package collection**:
The SFU-triggered step where peers generate and publish epoch key packages only
when an encrypted epoch needs them: at E2EE enable time, when joining an
encrypted room, or after reconnecting without epoch state.

**Epoch-capable peer**:
A peer whose browser and device identity state can generate and verify epoch
key packages, process epoch commits, and run the media transform required for
encrypted epochs. Non-epoch-capable peers cannot participate in encrypted
epochs.

**Epoch commit**:
The broadcast object authored by the designated committer to move the room from
epoch N to epoch N+1. It binds the expected previous epoch, next epoch,
SFU-published membership delta, resulting roster hash, group-state hash, and the
new meeting secret distribution material under the committer's epoch signature.
When MLS library objects are used, the commit carries opaque encoded MLS commit
bytes inside a Meet epoch envelope rather than exposing MLS internals to the
SFU.

**TreeKEM path update**:
The MLS-style mechanism used by the designated committer to rotate group secret
material for retained epoch members. The committer updates its tree path so
removed members cannot derive the next meeting secret, while retained members
derive it from their private path secrets instead of receiving per-member
envelopes.

**Ratchet tree**:
The epoch protocol's MLS-style binary tree of epoch members and parent secrets.
It uses TreeKEM path updates, parent hashes, a tree hash, and a confirmation
value so retained members can verify that an epoch commit describes one
consistent group state. Meet uses MLS-style ratchet tree semantics without RFC
9420 wire-format interoperability.

**Epoch protocol provider**:
The client-side library adapter responsible for MLS group-state operations:
creating genesis state, generating key packages, creating and processing
commits, joining from welcomes, maintaining ratchet-tree state, and exporting
the active meeting secret. Meet keeps SFU membership deltas, sender IDs, media
frame format, and product policy outside the provider.

**Epoch state**:
The in-memory client state needed to participate in the active epoch: ratchet
tree private path secrets, active meeting secret, epoch roster, and current
epoch number. Device identity is persisted separately, but epoch state is not
persisted to disk. A reload or reconnect that loses epoch state rejoins as a new
epoch member.

**Epoch reconnect**:
A reconnect or reload that loses epoch state creates a new epoch member. If the
SFU can correlate the old disconnected peer with the new peer within a short
grace period, it may batch the old peer removal and new peer addition into one
epoch transition.

**Genesis epoch**:
The first encrypted epoch of a room. When E2EE is enabled, the host creates
epoch 1 with its current peer as the first epoch member and publishes a signed
genesis epoch commit. Later joins use normal epoch transitions.

**Epoch welcome**:
A per-added-member encrypted object that gives a joining epoch member the secret
material needed to install the new epoch. It is encrypted to the joining
member's HPKE/X25519 init public key from their verified epoch key package.
When MLS library objects are used, welcomes are relayed as opaque encoded MLS
welcome bytes inside Meet epoch envelopes targeted to specific sender IDs.

## Relationships

- A **per-sender chain** plus a per-frame Ed25519 signature authenticates
  frames under threat model B. AES-GCM's tag alone is not sender
  authentication because every legitimate participant has the meeting secret.
- A meeting is *server-blind* by construction: the SFU has no key material,
  only proofs.
- The **meeting secret** is the root of the chain hierarchy. All chains
  derive from it; rotating it invalidates all downstream keys.
- The per-joiner ECDH is a *delivery channel* for the meeting secret, not
  the chain key itself. The chain is meeting-shared so the sender can
  encrypt once and the SFU can fan out to all joiners.
- Threat model B rules out threat model C as out of-scope: a single SFU
  cannot defend against itself.
- The **epoch protocol** rotates the **meeting secret**. Existing frame
  encryption remains derived from the active meeting secret, sender ID,
  media type, and frame generation.
- Chat E2EE derives from the same active **meeting secret** as media, using a
  separate HKDF context. Rotating epochs rotates both media and chat secrets.

## Flagged ambiguities

- "end-to-end encryption" is used loosely in the codebase to mean both
  "the SFU can't read the media" (server-blind) and "no participant can
  impersonate another" (per-sender chain). Resolved: v2 implements both
  under threat model B.
- "epoch_secret" in the refactor doc §2 is the meeting-shared secret, not
  the per-joiner ECDH output. The per-joiner ECDH output is used only for
  envelope encryption.

Decisions without ADRs (easily reversible, not surprising, or no real alternative):

- **Threat model: B** (not A, not C).
- **No per-frame SFU signature.** Receiver-side per-frame Ed25519 verification
  closes the "skip the transform" hole while keeping the SFU server-blind. The
  signing public key must be bound to the SFU-assigned `sender_id`; clients must
  not trust self-asserted sender IDs from handshake payloads.
- **Fresh start, no migration.** The current passphrase-based implementation
  in `frontend/src/utils/media/e2ee.ts` is local-only and is replaced
  wholesale. There are no production v1 meetings to preserve. The new
  implementation ships as the only E2EE version; the refactor doc's
  "v1 ↔ v2 coexistence" scaffolding is unnecessary. The `e2ee_key_version`
  format is the new rotation counter (`v<n>-<8 hex>`, starting at `v1-` for
  the new code) and the `e2ee_key_proof` is the new ed25519 signature.
  The refactor's "v2-" prefix (as proposed in §3.1) is dropped — we just
  use the new format directly.
- **Host identity: per-device ed25519, no recovery.** The host generates a
  fresh ed25519 auth keypair on first E2EE use on each device, stores the
  private key in IndexedDB, and the public key in `tabUser.device_keys`
  (Frappe). A new device that hasn't enabled E2EE before has no auth
  keypair and can only *join* v2 meetings (using the host's meeting X25519
  pubkey) — it cannot *host* them. No cross-device recovery in v1; the
  human-shareable passphrase recovery story from the refactor doc §3.3 is
  deferred. "Lost device" means the meeting must be re-created from a
  device that does have the auth keypair.
- **X25519 in WebCrypto required, no P-256 fallback.** Older browsers
  (Chrome < 133, Firefox < 132, Safari < 17.4) are rejected from E2EE
  with a clear "update your browser" message. The E2EE toggle in
  `MeetingAccessSettingsTab.vue` shows a disabled state with a tooltip
  on unsupported browsers; the meeting itself still works in non-E2EE
  mode. No silent downgrade to P-256 — that would create a downgrade
  attack surface for participants who can choose to use the weaker
  primitive.
- **No passphrase UI.** The 16-char human-shareable passphrase is gone.
  ECDH is the only key agreement. The host's pubkey fingerprint is shown
  to joiners as the "are you in the right meeting?" check. The
  `E2EEKeyDialog` and the "Share key" UI in `MeetingAccessSettingsTab.vue`
  are removed; the 8-char-minimum validation in `Meeting.vue:290-295` is
  no longer needed.
- **Host-only admission in v1.** The host generates the meeting secret
  and is the only authenticated distributor in v1. Joiners accept an
  envelope only if it verifies against the server-published host Ed25519
  signing key and the server-published host X25519 public key. A current
  participant's self-supplied signing key is not an authenticated trust
  anchor under threat model B, so hostless admission is deferred until
  there is an authenticated responder roster, meeting-secret commitment,
  or epoch protocol. If the host is offline and no in-memory host secret
  is available, the joiner surfaces an `E2EE_KEY_HOLDER_TIMEOUT_MESSAGE`:
  "The meeting host is not online to provide the E2EE key. Ask the host
  to stay online, or recreate the meeting." The SFU relays the envelope
  opaquely and validates only payload shape/size and target sender.
- **Chain tips wiped on `pagehide`, re-ECDH on resume or after ~100
	missed frames.** Chain tips are per-frame AES keys; `meeting_secret` derives
	all frame keys. Persisting either to disk (even encrypted with another local
	IndexedDB key) is the same anti-pattern the v1 passphrase-in-localStorage
	model embodied. iOS Safari suspend/resume triggers a fresh ECDH; the cost is
	~10ms when the host is online, and a "reconnecting" indicator when the host is
	offline. If the host fully reloads and loses its in-memory `meeting_secret`,
	v1 cannot recover that encrypted epoch; the meeting must be recreated or a
	future epoch-transition protocol must rotate the secret for everyone. The
	`meet:e2ee-needs-key-resync` event (T4.3 in the refactor doc) is the trigger
	for the resync.
- **Sender ID is SFU-assigned.** The 4-byte `sender_id` in the frame
  header is assigned by the SFU at peer join. The SFU tracks the
  (sender_id → peer socket) mapping opaquely — it doesn't know the
  identity behind the sender_id, only the socket. No collision risk;
  ~8 bytes extra SFU state per peer. Alternatives considered: client-
  generated random 32-bit (collision risk) and SHA-256(ed25519_pub)
  prefix (algorithm-coupled). Both rejected as worse trade-offs.
- **Layer 3 MLS-style epoch transitions are out of scope for v1.** Automatic
  member-change rekey is deferred. Host-side forward secrecy, leave/kick
  forward secrecy, and post-compromise security remain deferred to Layer 3.
- **Layer 3 epoch protocol is MLS-style, not RFC 9420 interop.** The epoch
  protocol borrows MLS / TreeKEM concepts for group-state rotation, but keeps
  Meet's existing media frame encryption and server-blind SFU relay shape.
- **Epoch protocol may replace the unshipped frame header.** The current frame
  header has not shipped, so the epoch protocol can add an explicit epoch field
  without backward-compatibility scaffolding.
- **Media frames carry a 32-bit epoch number.** The epoch number is explicit in
  the frame header, starts at 1, increments for each accepted epoch transition,
  and is authenticated with the encrypted frame.
- **Media frames identify senders by SFU-assigned sender ID.** The frame header
  carries the sender ID, not a device ID or separate epoch member ID. The epoch
  roster binds sender IDs to epoch members and their verified device identities.
- **Per-frame Ed25519 signatures remain required.** The epoch roster binds
  sender IDs to verified frame signing keys, but AES-GCM alone still does not
  authenticate sender identity because all current epoch members know the active
  meeting secret.
- **Epoch transitions rotate chat E2EE too.** Chat and media derive from the
  same active meeting secret with separate HKDF info strings, so removing a
  member cuts off future encrypted media and chat together.
- **Epoch roster is delta-driven and commit-bound.** The SFU publishes the
  membership delta, clients apply it locally, and the designated committer signs
  the resulting roster hash in the epoch commit. Clients accept the commit only
  if their computed roster hash matches the signed hash.
- **Epoch transitions use commit plus separate welcomes.** The epoch commit is
  broadcast to current members and binds the previous epoch, next epoch,
  membership delta, roster hash, group-state hash, and committer signature.
  Added members receive separate epoch welcomes encrypted to their verified
  HPKE/X25519 init public keys.
- **Existing members receive new epoch secrets through TreeKEM path updates.**
  Retained members derive the next meeting secret from MLS-style path update
  material, rather than receiving one HPKE envelope per retained member. This is
  the core mechanism that gives removals and post-compromise recovery their
  MLS-style shape.
- **Ratchet tree semantics are MLS-style, not approximate.** Epoch commits use a
  binary ratchet tree with path secrets, parent hashes, tree hash, and a
  confirmation value to detect malformed or inconsistent commits under threat
  model B. Meet may define compact project-specific wire objects, but preserves
  the MLS-style cryptographic invariants.
- **MLS internals come from a library behind an adapter.** Meet should not roll
  its own TreeKEM/key schedule if a viable browser TypeScript MLS library can
  provide those internals. The epoch protocol provider owns library integration,
  while Meet owns SFU deltas, sender IDs, roster binding, media frame headers,
  and chat/media secret derivation.
- **SFU relays Meet epoch envelopes, not parsed MLS internals.** Epoch commits
  and welcomes are wrapped in Meet metadata such as epoch number, membership
  delta ID/hash, roster hash, and target sender ID. MLS commit/welcome bytes are
  opaque to the SFU; clients validate both the MLS group state and the Meet
  membership/roster binding.
- **The active meeting secret is derived through the MLS exporter.** The epoch
  protocol provider exposes a 32-byte meeting secret for media and chat by using
  an MLS exporter with a Meet-specific label/context. Meet does not use raw MLS
  epoch secrets directly and does not send a separate meeting secret in epoch
  commits or welcomes.
- **Epoch state is memory-only.** Clients persist device identity, but not
  ratchet tree private secrets, active meeting secrets, or epoch rosters. A
  reload or reconnect that loses epoch state publishes a new epoch key package
  and joins through a fresh epoch transition.
- **Reconnects may batch remove+add.** If a client reloads or reconnects and
  loses epoch state, it rejoins as a new epoch member. When the SFU can
  correlate the old and new peers during a short grace period, it batches the
  old member removal and new member addition into one epoch transition;
  otherwise they proceed as separate transitions.
- **New encrypted rooms start with a host-created genesis epoch.** When E2EE is
  enabled, the host publishes its epoch key package and signs a genesis commit
  creating epoch 1. Additional peers join through ordinary epoch transitions;
  the current host-only v2 envelope path is not a separate compatibility mode.
- **Epoch protocol replaces current v2 admission.** The current host-only
  envelope admission path has not shipped and should not coexist with epoch
  admission. Encrypted rooms always start with a genesis epoch and later joins
  use epoch transitions.
- **Epoch protocol implementation uses tracer bullets.** Build the smallest
  end-to-end vertical slice for each capability rather than a big-bang rewrite:
  genesis epoch, add member, remove member, reconnect/resync, then TreeKEM
  hardening. Each slice should include crypto-domain tests and integration
  wiring for the behavior it introduces.
- **The first epoch tracer bullet is genesis-only.** The first implementation
  slice replaces E2EE enable with a host-created epoch 1 for the host's current
  peer, adds the epoch number to media frames, installs the epoch 1 meeting
  secret, implements the full ratchet tree module, and keeps host media/chat
  encryption working. Join, remove, and reconnect/resync wiring come after the
  genesis slice.
- **Threat model remains B for the epoch protocol.** Malicious SFU equivocation
  and fork detection remain out of scope unless a future consistency layer is
  added.
- **Epoch membership is SFU-authoritative, client-authenticated.** The SFU is
  the product source of truth for room presence, sender IDs, and kicks, but
  clients cryptographically verify epoch commits and the SFU never sees media
  key material.
- **Epoch commits are authored by a designated committer.** The SFU chooses an
  online current epoch member, preferring the host, to produce the next epoch
  commit. This avoids a permanent host-online requirement while preventing
  arbitrary members from racing conflicting commits.
- **Committer failure triggers redesignation.** If the designated committer
  times out or disconnects, the SFU designates another online current epoch
  member rather than failing the join/rekey or asking multiple committers in
  parallel. Parallel commits are avoided to keep ordering and rollback simple.
- **Only one epoch transition is in flight per room.** The SFU may briefly
  batch nearby joins/leaves before designating a committer, then queues later
  changes for the next epoch. Clients validate a commit against exactly one
  expected previous epoch and one SFU-published membership delta.
- **Epoch transitions use receiver-tolerant overlap.** Senders switch to the new
  epoch immediately after installing it. Receivers accept the previous epoch and
  current epoch for a short bounded window to avoid freezing media during
  propagation jitter, then wipe the previous epoch.
- **Epoch activation is not acknowledgement-gated.** A valid commit/welcome is
  active for a client as soon as it is accepted locally. The SFU may track epoch
  acknowledgements for diagnostics and retries, but one slow or stuck peer does
  not block the room from moving to the new epoch.
- **Missed epoch commits use retry plus client resync.** The SFU retries
  unacknowledged commits and welcomes for a short window. Clients that receive
  media from an unknown epoch request epoch resync; if the missing epoch state
  is no longer recoverable, they rejoin as new epoch members.
- **Epoch material retention is short-lived.** The SFU retains only opaque
  commit/welcome objects and acknowledgement state for the latest few epoch
  transitions or a short TTL, enough for transient retry/resync but not full
  meeting history.
- **Epoch membership is per live peer.** Each epoch member is one SFU peer/socket
  bound to a per-device identity and SFU-assigned sender ID. User-level product
  actions like kick may remove multiple epoch members, but the cryptographic
  membership unit remains the live peer.
- **Epoch members authenticate with existing device identity.** A joining peer
  signs its epoch key package with its existing per-device Ed25519 identity key.
  The SFU remains authoritative for sender ID and room membership, but clients
  verify the device signature before accepting the member into an epoch.
- **Epoch key packages are live-only MLS-style packages.** A key package
  contains the member's device identity public key, epoch signing public key,
  HPKE/X25519 init public key, leaf public key, sender ID, user ID, and device
  ID, signed by the existing per-device Ed25519 identity key. Offline one-time
  prekeys are omitted because Meet admission is live.
- **Epoch key packages are published lazily.** Peers do not publish epoch key
  packages for non-E2EE rooms by default. The SFU requests key packages when
  E2EE is enabled, when a peer joins an encrypted room, or when a reconnecting
  peer needs to join a fresh epoch.
- **E2EE enable requires all current peers to be epoch-capable.** If any current
  peer cannot publish a valid epoch key package, E2EE enable is blocked with a
  clear browser/device support error. Peers joining an already encrypted room
  are rejected before media setup if they are not epoch-capable. Fallback crypto
  remains rejected by ADR-0005.
